# Detection Validation Plan

## 1. Purpose

This document defines how to review Windows telemetry generated by the safe lab actions mapped to selected MITRE ATT&CK techniques. The validation is performed locally using Windows Event Viewer and PowerShell.

The plan separates three different outcomes:

1. **Execution confirmed** — the test action completed and its functional result was observed.
2. **Logging confirmed** — a relevant Windows event was found in the expected event log.
3. **Detection confirmed** — an EDR or SIEM detection/alert was generated and independently verified.

A successful command or marker does not automatically prove that Windows logged it. A Windows event does not automatically prove that an EDR/SIEM alert was generated. Each claim must be supported by evidence.

## 2. Scope

The validation scope is limited to:

- One personal Windows computer.
- Benign, local PowerShell commands.
- An already-authorized local user session.
- A temporary user-level Registry Run value that launches a harmless marker script.
- A synthetic text file and an optional HTTP receiver bound to `127.0.0.1`.
- Manual review of Windows event logs.

The exercise does not include domain scanning, credential access, lateral movement, defense impairment, external file transfer, or unauthorized access. MITRE CALDERA and a separate SIEM/EDR platform were not part of the confirmed lab setup.

## 3. Event Sources and Relevant Event IDs

| Source | Event ID | What it can show | Prerequisites / caveats |
|---|---:|---|---|
| Windows Security | 4624 | Successful logon | The event should be correlated with the correct time, account, and logon type. It does not establish how the account was obtained. |
| Windows Security | 4688 | Process creation | Process-creation auditing must be enabled. Command-line details require the relevant command-line auditing policy. |
| PowerShell Operational | 4104 | Script block logging content | PowerShell Script Block Logging must be enabled. Not every command or context will necessarily produce an easily identifiable record. |
| PowerShell Operational | 4103 | Module logging details | Module Logging must be configured for the relevant modules. It is not enabled by default in every environment. |
| Sysmon | 1 | Process creation | Sysmon must be installed and its configuration must collect the relevant process events. |
| Sysmon | 12 | Registry object creation or deletion | Depends on Sysmon installation and the configured registry event filters. |
| Sysmon | 13 | Registry value set | Useful for observing a Run value being created or modified, subject to the Sysmon configuration. |
| Sysmon | 14 | Registry key/value rename | Not expected for every registry change; depends on the action and configuration. |
| Windows Security | 4657 | Registry value modification | Requires the appropriate audit policy and a SACL on the target registry key/value. It is not guaranteed by default. |
| Sysmon | 3 | Network connection | Requires a Sysmon configuration that collects NetworkConnect events. Loopback behavior may differ from external network traffic and does not establish exfiltration. |
| Windows Filtering Platform | 5156 | Allowed network connection | Requires Filtering Platform Connection auditing. Availability depends on audit policy and filtering configuration. |

Events may be absent because of audit configuration, permissions, Windows version, event retention, or endpoint-agent settings. Missing telemetry should be recorded as an observability limitation, not as proof that the action did not occur.

## 4. Validation by Scenario Phase

### 4.1. Authorized-account context — T1078.003 (behavioral analogue)

**Action:** sign in to an already-authorized local account and run benign commands such as `whoami`, `hostname`, and `Get-Date`.

**Review:**

- Security Event ID 4624 around the sign-in time.
- Security Event ID 4688 for PowerShell process creation, if enabled.
- PowerShell Operational Event ID 4104, if Script Block Logging was enabled.

**Validation criterion:** the account/session context and subsequent PowerShell activity can be correlated by time and host where the relevant logs are available.

**Limitation:** this test does not validate how an attacker obtained the account or gained initial access. It is only an authorized-account context simulation.

### 4.2. PowerShell execution — T1059.001

**Action:** execute benign PowerShell commands with unique lab markers and create harmless test files.

**Review:**

- PowerShell process creation in Security 4688 or Sysmon 1, if configured.
- PowerShell Operational Event ID 4104 for script block content, if enabled.
- Event ID 4103 where Module Logging is configured.
- User, timestamp, host, process lineage, and command line where collected.

**Validation criterion:** the test command execution can be associated with the correct local user session and test time using available telemetry.

### 4.3. Persistence — T1547.001

**Action:** create the temporary value `APT29-LAB` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, use it to launch a harmless marker script at logon, sign out and back in, then remove the test value and artifacts.

**Review:**

- Sysmon Event IDs 12/13/14, if the relevant registry events are enabled in the Sysmon configuration.
- Security Event ID 4657, if registry auditing and the required SACL are configured.
- Security Event ID 4688 or Sysmon Event ID 1 for the related process execution, if configured.
- PowerShell Operational Event ID 4104 for relevant PowerShell blocks, if enabled.
- The marker file `%TEMP%\APT29-LAB-PERSISTENCE.txt` as functional evidence that the script ran.

**Execution criterion:** the marker file appears after the subsequent logon. This was observed during the lab; the terminal displayed:

```text
APT29-LAB-PERSISTENCE 30.10.2026 1:04:49,25
```

**Detection criterion:** a relevant registry or process event is actually found in the configured event source. The presence of the marker file alone is not proof that a security event or alert was generated.

### 4.4. Local synthetic file transfer — auxiliary test, not T1048.002 validation

**Action:** send a synthetic text file to a Python HTTP receiver bound to `127.0.0.1:8088` on the same computer.

**Review:**

- Actual HTTP response status from the sender.
- Whether the receiver created the output file.
- Whether SHA-256 hashes of the source and received files match.
- Process and network telemetry, if the relevant auditing is available.

**Critical limitation:** loopback traffic remains inside the same host. This test is not data exfiltration to an external system and does not validate T1048.002. The APT29 procedure associated with the SolarWinds Compromise involved HTTPS transfer to an archive staged on a victim OWA server. The lab did not reproduce that procedure.

## 5. Manual Windows Log Review

### 5.1. PowerShell Operational — Event ID 4104

The following command searches the last six hours for PowerShell script-block events:

```powershell
$since = (Get-Date).AddHours(-6)

$events = Get-WinEvent -FilterHashtable @{
    LogName   = 'Microsoft-Windows-PowerShell/Operational'
    Id        = 4104
    StartTime = $since
} -MaxEvents 100 -ErrorAction SilentlyContinue

$events | Select-Object TimeCreated, Id, Message | Format-List
```

To export the returned events, if any:

```powershell
$evidence = Join-Path $env:USERPROFILE 'Documents\APT29-Lab-Evidence'
New-Item -ItemType Directory -Path $evidence -Force | Out-Null

$events |
    Select-Object TimeCreated, Id, Message |
    Export-Csv (Join-Path $evidence 'powershell-4104.csv') `
        -NoTypeInformation -Encoding UTF8
```

If `$events` is empty, possible explanations include Script Block Logging not being enabled, the events falling outside the selected time window, or the relevant script blocks not being recorded. An empty query is not proof that the commands did not execute.

### 5.2. Security log — Events 4624 and 4688

In Event Viewer, open:

`Windows Logs → Security`

Filter around the test time for Event IDs 4624 and 4688. For Event ID 4688, check whether command-line information is present. If process-creation auditing was not enabled before the test, record that limitation instead of claiming the event was collected.

### 5.3. Registry telemetry

If Sysmon is installed, open:

`Applications and Services Logs → Microsoft → Windows → Sysmon → Operational`

Review Events 12–14 around the time the test Run value was created and removed. For Security Event ID 4657, remember that the applicable audit policy and SACL must have been configured beforehand.

## 7. Result Definitions

- **Pass:** the action ran and its expected functional result is supported by evidence.
- **Fail:** the test was executed, but the expected functional result was not achieved.
- **Not verified:** the result could not be confirmed because of missing logs, audit settings, permissions, or saved evidence.
- **Detection gap:** the action ran and relevant telemetry was available, but the expected detection rule or alert did not trigger. Use this label only after checking the actual SIEM/EDR integration and rule behavior.

## 8. Cleanup and Residual-Artifact Checks

The lab cleanup included:

- Removing the `APT29-LAB` value from the current user's Run key.
- Removing `%TEMP%\APT29-LAB-PERSISTENCE.txt`.
- Removing the `APT29-Lab` working directory.
- Retaining `Documents\APT29-Lab-Evidence`.
- Stopping the local Python HTTP receiver.

The final path checks returned:

```text
APT29-Lab: False
Documents\APT29-Lab-Evidence: True
```

For an additional check that the Run value is absent:

```powershell
Get-ItemProperty `
    -Path 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Run' `
    -Name 'APT29-LAB' `
    -ErrorAction SilentlyContinue
```

The command should not return an `APT29-LAB` value. Windows event logs should not be deleted as part of cleanup.

## 9. Limitations

- The test was conducted on one Windows computer; no separate SIEM/EDR deployment was validated.
- Event availability depends on audit policies, PowerShell logging settings, Sysmon installation/configuration, and log retention.
- The local HTTP test does not represent data leaving the host.
- C2 infrastructure, encrypted external exfiltration, defense evasion, lateral movement, and credential compromise were not tested.
- CALDERA was not used; the actions were performed manually.

## 10. Recommendations for Further Validation

1. In a dedicated lab, enable and verify PowerShell Script Block Logging and process-creation auditing before running the tests.
2. If authorized, deploy Sysmon with a documented configuration that collects process creation, relevant registry changes, and network connections.
3. If a SIEM is available, ingest Windows Security, PowerShell Operational, and Sysmon events and correlate them by host, user, process, and timestamp.
4. If external data-transfer behavior must be studied, design a separate test between two isolated systems using synthetic data and an approved receiver. Do not label a localhost transfer as exfiltration.
5. If automation is required, repeat only the safe actions through MITRE CALDERA in an isolated lab after reviewing each ability.
